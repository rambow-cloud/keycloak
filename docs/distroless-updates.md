# Distroless runtime updates and CVE comparisons

The owner authorizes a new image revision for a changed **distroless runtime digest within the reviewed Java/Debian nonroot family**, even if no CVE disappears. This narrow exception keeps published runtime bytes current. Builder-only updates, Keycloak/version maintenance alone, documentation and unchanged inputs do not independently authorize releases. Ordinary main pushes still do not upload images; runtime automation creates a formal Release only after verified evidence passes.

## Update and comparison

The hourly upstream workflow runs the dedicated runtime updater first. It compares the latest same-family runtime digest with the effective latest publication independently for core/aws, applying withdrawals and architecture expansions. A compliant Maintenance Issue and App-owned `fix/<issue>-distroless-<identity>` PR change only `images.lock.json`, `config/runtime-update.json` and a new immutable `changes/<issue>-distroless.json`. The fragment uses `type: runtime-update`, explicit profiles and `runtime.from`/`runtime.to` pins. An already merged but unpublished runtime can be reconciled without changing its lock again. The generic updater handles Keycloak/builder maintenance and leaves runtime locks to this path.

Native required CI builds selected images with Buildah and verifies them with Podman. For an active runtime request it pulls the exact published child with Skopeo, installs the checksum-pinned native Trivy once, scans the baseline with a fresh database cache, then scans the candidate with both database updates disabled. SHA-256 hashes of the vulnerability and Java database bytes must remain identical. Both scans require matching Linux architecture, Debian and Java inventories and matching OCI/config digests. The normal candidate HIGH/CRITICAL and coverage gates remain mandatory; baseline findings do not prevent testing their repair.

The existing `trivy-<profile>-<architecture>-<attempt>` artifacts retain full `before.json`, candidate `trivy.json`, database metadata and `runtime-pair.json`. The latter retains compact inventories/findings, original full-report hashes, source/run/attempt, exact before/after child digests, scanner checksum and database hashes. PR/main job summaries show resolved and newly detected CVEs. A profile-wide resolved claim requires the CVE absent from **both** candidate architectures. Counts are package findings, not exploitability determinations; removed components and other inherited source changes can explain disappearance. Updating a digest alone never proves a CVE repaired.

Unchanged identities and existing candidate Issues/PRs are preserved without another build or overwrite. Edited candidate bodies, files or commits revoke native auto-merge through trusted Issue policy. Same-family digest merges retain the existing required-check authorization; changed startup support, Java/base families and larger upgrades require separate review. A stale or failed candidate is left for explicit review/recovery rather than automatically retried or force-pushed.

## Formal publication

[Distroless runtime release](https://github.com/rambow-cloud/keycloak/actions/workflows/runtime-release.yml) accepts successful main CI completion or a manually supplied successful source run ID on main. It validates repository/workflow/event/source-main ancestry, complete expected native report artifacts, exact attempts, current publication bindings and packaged multiarchitecture artifact availability. Only trusted default-branch code parses reports with the App token; artifact JSON is never executed. Read-only comparison jobs receive neither App nor registry credentials.

Automatic PR/fork/non-main CI completions are ineligible and skipped before any credentialed job. Successful main metadata-only CI without image artifacts also skips; it is not scan evidence. Partial, expired, wrong-attempt or malformed image artifacts still fail closed. Explicitly supplied invalid manual source runs remain errors.

After independent report validation, the pinned updater App creates a draft `v<Keycloak>-r<N>` Release, uploads immutable `runtime-comparison.json`, and makes it formal. The next revision accounts for both recorded publications and existing Release tags; collisions and conflicting evidence fail. Release creation serializes with itself and defers while an earlier Quay publication is active, without occupying/cancelling the publisher's concurrency slot. Recover a deferred source run after that catalog completes. Existing matching Releases are preserved, not recreated. A draft interrupted before completion can be recovered from the same source evidence; an expired or changed source attempt requires explicit review, not an old-success fallback.

Release notes list runtime pins and actual per-profile resolved/introduced CVEs. **No CVE repairs were detected** is an acceptable, explicit runtime-update result. Upstream changelogs are supplemental context; they do not replace actual final-image comparison evidence.

The existing Quay workflow handles the formal Release. It reuses exact source OCI artifacts, freshly scans every selected architecture with the current policy/database, requires all claimed repaired CVEs still absent, and checks its inspected child digests equal the compared children before freezing/publishing. The frozen plan includes the runtime comparison hash and measured CVE history. Immutable tags, OIDC-only Quay authentication, partial-upload recovery and required catalog PR completion remain unchanged. A newer fixable HIGH/CRITICAL advisory can still block publication after comparison.

Only the validated report hash and expected per-profile children cross job outputs/environment variables. Full findings and inventories remain in the immutable Release asset and source artifacts; this avoids Linux environment-string limits while preserving the complete evidence binding.

Open the formal Release to view its notes and download `runtime-comparison.json`; the report includes exact source CI links. Full original raw reports expire with source CI artifacts; the compact immutable Release attachment remains available.

## Git repair history and recovery

After successful Quay catalog completion, automation opens a separate compliant Maintenance Issue and documentation PR retaining `releases/evidence/<release>-runtime.json` and updating the homepage image table. For actually resolved CVEs it appends exact published index/profile records and concise security release notes, generating both security documents. A zero-observed-fix runtime update adds comparison evidence without inventing a security repair. These documentation PRs require normal review; the tightly scoped Quay catalog auto-merge exception is not broadened. Human edits and prior Issues/branches are preserved.

For an interrupted producer, run **Distroless runtime release → Run workflow → main** with its successful exact main CI run ID. For registry/catalog recovery use **Quay release** with the existing formal tag. After successful formal-tag publication, a missing Git report can be recovered by giving its successful Quay run ID to the runtime workflow. For a main-only Quay recovery run, also supply the formal `release_tag` to identify the completed Release explicitly. Automatic early duplicate-event callbacks defer until publication/catalog evidence exists; explicit manual recovery with missing/conflicting evidence remains an error. No recovery changes published bytes or tag bindings.
