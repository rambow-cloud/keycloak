# AWS RDS for PostgreSQL

The `core` profile supports password authentication with the PostgreSQL driver bundled by Keycloak. The `aws` profile adds AWS Advanced JDBC Wrapper 4.5.0 and SDK 2.46.10 for task-role IAM authentication. Both remain Java 25, distroless, and UID 65532 images built with Buildah. The AWS image includes a checksum-pinned **public** RDS CA bundle and defaults to verified database TLS; no credentials are baked in.

The AWS dependency graph explicitly pins Apache HttpClient 5.6.4 and HttpCore/HTTP2 5.4.4 to remediate CVE-2026-54399, CVE-2026-54428 and CVE-2026-64607. These stable patch overrides are recorded in the POM and SHA-256 lock. The AWS build exercises the real SDK Apache HTTP transport against a loopback fixture before optimization; it uses no cloud credentials. Both resulting images must pass the [Trivy gate](vulnerability-scanning.md).

The initial reference is PostgreSQL 17 on a standard RDS PostgreSQL instance, including ordinary Multi-AZ instance endpoint reconnection. Aurora, RDS Proxy, and Multi-AZ DB clusters require separate validation. Local CI verifies both drivers with PostgreSQL/TLS fixtures and exercises IAM signing with fake credentials, expecting PostgreSQL to reject the generated token. Real RDS IAM and Fargate certification remains pending staging results.

## Password authentication

Use [rds-password.env.example](../examples/rds-password.env.example) with the core image. Supply the actual RDS writer endpoint, dedicated database and username. Inject `KC_DB_PASSWORD` from a runtime secret store. Mount the RDS CA bundle read-only at `/run/certs/rds-ca.pem`, readable by UID 65532. Do not put credentials in the JDBC URL or checked-in environment files.

Keycloak 26.8.1 supports `KC_DB_TLS_MODE=verify-server` and `KC_DB_TLS_TRUST_STORE_FILE`; PostgreSQL expects a PEM CA file. These native settings perform full certificate and hostname verification. Do not combine them with JDBC options that disable or weaken TLS. See [Keycloak database TLS](https://www.keycloak.org/server/db) and [RDS TLS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.SSL.html).

The AWS profile can also use password authentication with the wrapper URL and `?wrapperPlugins=` (empty plugin list), runtime database password, and its bundled CA. This is useful on Fargate when a separate CA volume is unavailable; the core profile remains the smaller generic option.

## IAM authentication on ECS/Fargate

Use [rds-iam.env.example](../examples/rds-iam.env.example) with the AWS image. `KC_DB_DRIVER` and disabled XA are already baked into that profile. Use `jdbc:aws-wrapper:postgresql://<rds-endpoint>:5432/keycloak?wrapperPlugins=iam`; omit `KC_DB_PASSWORD` and static AWS access keys. Use the actual RDS endpoint, not an IP or custom DNS alias, for token signing and certificate verification.

Prerequisites, performed by the database/cloud administrator:

1. Enable IAM database authentication on RDS. Allow network traffic from the task security group to the database port through private VPC routing.
2. Create a dedicated IAM database user, grant it `rds_iam`, and make it owner of the Keycloak database/schema or grant the DDL/DML privileges needed by schema initialization and migrations. Keycloak must be able to create/alter its tables and indexes and use its migration locks. Do not grant RDS administrative privileges to the application.
3. Grant the **task role**, not just the execution role, `rds-db:connect` for the database user's resource ARN. The ARN uses the RDS **DB resource ID**, not the instance name:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "rds-db:connect",
    "Resource": "arn:aws:rds-db:REGION:ACCOUNT_ID:dbuser:DB_RESOURCE_ID/keycloak_iam"
  }]
}
```

4. Set `AWS_REGION` to the database region. The SDK uses the ECS container credential provider and refreshes temporary credentials. Database IAM tokens are generated by the wrapper when needed; do not generate a token once and store it as a permanent password.

Use different database users for password and IAM modes: granting `rds_iam` makes IAM authentication take precedence over password authentication for that PostgreSQL user. Tokens last 15 minutes, but existing connections remain valid after token expiry. See [AWS IAM authentication](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.html) and [SDK credential resolution](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/credentials-chain.html).

## ECS/Fargate task example

[ecs-rds.task-definition.json](../examples/ecs-rds.task-definition.json) is a replace-the-placeholders template for Linux x86_64, 1 vCPU and 2 GiB RAM. It does not provision or register anything. Supply an AWS-profile image by digest in a registry accessible to the task, existing IAM roles, log group, bootstrap secret, endpoint, hostname and ALB subnet CIDRs.

For an ARM64 task, set `runtimePlatform.cpuArchitecture` to `ARM64` while retaining `operatingSystemFamily: LINUX`, and select the `v26.8.1-r3` or newer multi-architecture AWS image index by digest. The template keeps its x86_64 default. Check [AWS ARM64 task requirements and availability](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-arm64.html); native image CI does not replace live RDS/Fargate staging verification.

- Keep `readonlyRootFilesystem=true`, user 65532, and dropped capabilities. The image declares `/tmp` and `/opt/keycloak/data` as volumes with image directory permissions for ECS volume initialization. Mount task-local writable volumes at those exact paths. They are ephemeral and must not be used as database storage. See [ECS volume initialization](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html).
- Terminate HTTPS at ALB, forward application traffic to 8080, and permit only ALB security groups to reach task application/management ports. `KC_PROXY_TRUSTED_ADDRESSES` must match the ALB subnet ranges. Do not expose management port 9000 through a public listener.
- Configure ALB target health checks on port 9000 at `/health/ready`, startup grace period 180 seconds, deregistration delay 30 seconds, and task stop timeout 120 seconds. Tune grace periods from measured migrations/startup. Use external ALB checks; the image has no shell or curl for ECS command health checks.
- Bootstrap administrator credentials apply only during initial creation. Remove the bootstrap secret from normal task revisions once a permanent administration/recovery procedure is established. The execution role needs permissions to pull images, write logs, and retrieve any injected Secrets Manager secrets; the task role supplies database IAM credentials.
- Keep the database private. Budget pool connections across all tasks: `task count * KC_DB_POOL_MAX_SIZE` plus migration/admin headroom must fit available RDS connections. The example maximum of 20 is a starting point, not a universal tuning recommendation. `KC_DB_CONNECT_TIMEOUT` defaults to 10 seconds. Do not set the pool lifetime below 15 minutes solely because IAM tokens expire; token expiry does not invalidate an established session.
- Logs go to stdout/stderr and CloudWatch. Do not enable SQL/SDK credential tracing. Replace the image or override the read-only CA file path when CA bundles rotate; refresh the committed CA checksum through a maintenance Issue.

In a browser, open `https://YOUR_HOST/realms/YOUR_REALM/.well-known/openid-configuration` and confirm the HTTPS issuer and endpoint URLs. Open `https://YOUR_HOST/admin/` and confirm login/redirects. Check readiness through the private management route or ALB target status.

## External staging verification

The verifier runs with Node.js 22+ **outside** the production image against an existing HTTPS staging Keycloak deployment connected to RDS. It creates and deletes one uniquely named test realm, client, and temporary users. Use a dedicated staging administrator and database; no cloud infrastructure is created. It validates schema usability, writes, discovery, and cryptographically signed client-credentials tokens. It does not claim that a live database migration between Keycloak versions was tested.

```sh
export VERIFY_ALLOW_MUTATION=dedicated-staging
export VERIFY_BASE_URL=https://YOUR_STAGING_HOST
export VERIFY_ADMIN_USERNAME=YOUR_STAGING_ADMIN
read -r -s -p 'Staging admin password: ' VERIFY_ADMIN_PASSWORD
export VERIFY_ADMIN_PASSWORD
node scripts/verify-external.mjs
```

For an IAM renewal acceptance run, configure the dedicated staging task with `KC_DB_POOL_INITIAL_SIZE=0`, `KC_DB_POOL_MIN_SIZE=0`, `KC_DB_POOL_MAX_SIZE=1`, and `KC_DB_POOL_MAX_LIFETIME=10s`. Then run:

```sh
export VERIFY_IAM_REFRESH=true
export VERIFY_DURATION_SECONDS=960
node scripts/verify-external.mjs
```

The long run performs writes and authentication every 30 seconds for at least 16 minutes. Correlate it with database connection telemetry to confirm fresh connections after the original token expires. Also observe task-role credential renewal across its actual credential lifetime; a 16-minute test alone cannot prove ECS credential renewal. Restore normal pool settings afterward. A successful local fixture or long-running token test is not a substitute for those AWS staging observations.

For migration acceptance, snapshot the staging database, run the old supported image to create representative realms/users, stop it, then start the candidate image against the same database and run this verifier. Retain database rollback procedures; do not re-import users into a replacement database as an upgrade strategy.
